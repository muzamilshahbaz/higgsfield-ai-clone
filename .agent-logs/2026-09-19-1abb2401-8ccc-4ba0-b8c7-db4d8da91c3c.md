**Phase 2 · Generation core** (hours 7–13 in [docs/PLAN.md:324](docs/PLAN.md:324)) — the phase that makes the app actually *do* something. It's the next one up; Phases 0 and 1 are committed.

**What gets built**

- **AI provider port** — the `AIProvider` interface (`submit` / `poll` / optional `cancel`), `resolveProvider()` reading `AI_PROVIDER` and falling back to `mock` when a key is missing, plus `lib/ai/registry.ts` (the model catalog: id, task, cost, latency, capabilities). Presets and UI reference models by registry id only, so adding fal later is a registry edit plus one driver file.
- **Mock driver** — deterministic: progress derived from elapsed time since `started_at`, returns bundled sample clips, and fails ~1 in 12 on purpose so the refund path is demonstrable.
- **Three services** — `generation.service` (create/sync/list), `credits.service` (spend/refund/balance via the SQL functions), `asset.service` (media into our own Storage bucket, since provider URLs expire).
- **Routes** — `POST /api/generations` (auth → zod → rate limit → resolve preset/model/cost → `spend_credits` → insert `queued` → `provider.submit()`, refunding on throw), the `/sync` poller, and the image upload route.
- **UI** — the composer, job cards, a Supabase Realtime subscription on `generations(user_id=eq.me)`, and `use-job-ticker` POSTing `/sync` every 3s while any job is non-terminal.

**Key design point:** credits are debited *before* submit and refunded idempotently on failure or timeout; `idempotency_key UNIQUE` makes a double-submit a no-op. Because Vercel has no long-running worker, jobs advance through three layers — client ticker (primary), opportunistic sweep on page load, and the daily cron as a backstop.

**Done when:** text→image and image→video each succeed, fail, and refund correctly, and cards update live without a refresh.
