It isn't the model — they license the same third-party models everyone else does. The product *is* the **preset layer**: cinematic camera moves and visual styles packaged as one-click cards with autoplaying video previews. Five traits carry the whole experience:

## 4. Database schema

Plan rewritten at revision 2 — [docs/PLAN.md](docs/PLAN.md). Firebase turns out to be a *better* fit for this product than the Postgres plan it replaces, plus it absorbs the auth work. Here's what moved.

**Firestore upgrades the most important interaction.** The job feed was going to poll a status endpoint every 2 seconds. Now the client subscribes with `onSnapshot`, the server writes the status transition, and the card flips the instant it happens — less code, lower latency, and the Explore feed becomes live too (new public generations appear without a refresh). That's a demo moment the previous plan couldn't produce.

**Firebase Auth replaces Auth.js entirely** and gives you exactly the Google + email/password you asked for. It also closes both gaps I flagged last turn: password reset and email verification ship for free, so they're back in scope. We no longer hash passwords ourselves, and the JWT-session wrinkle disappears — we use Firebase session cookies instead.

**The `UNIQUE` constraints map onto document IDs**, which is the part of the SQL→NoSQL translation most likely to be fudged, so I made it explicit:

| SQL constraint | Firestore |
|---|---|
| `generation.idempotencyKey` | Generation doc ID *is* the key — a double submit throws `ALREADY_EXISTS` |
| `(generationId, reason)` on the ledger | Ledger doc ID is `${generationId}__${reason}` — a retried refund cannot double-refund |
| `(userId, generationId)` on likes | Doc ID is `${uid}__${generationId}` |

**One real problem Netlify introduces:** serverless has no long-lived worker to advance a job from `queued` to `succeeded`. Three layers cover it — a client-side sync ticker while the tab is open (snappy), a 1-minute Netlify Scheduled Function as the safety net for closed tabs and 6-minute timeouts, and a webhook route that stays dormant until a real provider is enabled. Netlify's public URL actually makes that webhook viable later, which the local-only plan couldn't do.

**Security posture:** every Firestore collection is `write: never` in the rules. The Admin SDK bypasses rules, so the server is the only writer while the browser still gets live reads — the client can watch its credits but can never mint them.

Three risks worth knowing before we start:

1. **Cloud Storage for Firebase may require the Blaze (pay-as-you-go) plan** on recently created projects — I'm not certain of the current cutoff, so verify it in Phase 0. If you'd rather not enable billing, the storage port swaps to Netlify Blobs with no other code change. Low impact this sprint regardless, since on the mock provider outputs are bundled clips and Storage only handles your uploads.
2. **No Java on this machine, so the Firebase Local Emulator Suite won't run.** Local dev goes against a real `kinetic-dev` project (Spark tier, free). Installing a JRE later unlocks offline dev but isn't on the critical path.
3. **Missing composite indexes are hard runtime failures in Firestore**, so all six are declared and deployed in Phase 0 rather than discovered at hour 21.

Phase 0 grew to 4 hours to absorb Firebase wiring; Phase 5 now covers the Netlify deploy and adding the `*.netlify.app` domain to Firebase's authorised domains — a 30-second step that, when forgotten, looks exactly like a total auth outage.
