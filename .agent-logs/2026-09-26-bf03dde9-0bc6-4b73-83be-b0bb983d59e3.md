Your app makes exactly two calls to Hugging Face, which is what the token has to satisfy:

- `GET huggingface.co/api/whoami-v2` — the key check on save
- `POST router.huggingface.co/hf-inference/models/{model}` — the generation

**Easiest answer: create a classic "Read" token.** It covers both, and there are no permission checkboxes to get wrong. Unless you have a policy reason to scope tightly, do that and skip the rest of this.

**If you use a fine-grained token,** tick exactly these:

| Section | Permission | Why |
|---|---|---|
| **Inference** | ✅ **Make calls to Inference Providers** | Required. Without it the token authenticates and then gets refused at generation. |
| **Repositories** | ✅ **Read access to contents of all public gated repos you can access** | Only needed for **FLUX.1 [dev]** (`lumen-pro`, `lumen-portrait`). Skip it if you're only using Lumen Flash / Lumen SDXL. |

Leave everything else **off** — no write access, no *Manage Inference Endpoints*, no billing, webhooks, collections, discussions, or org permissions. None of them are touched by this app.

Two gotchas worth knowing:

1. The gated-repo permission is **not a substitute for accepting the licence.** For FLUX.1 [dev] you need both: accept it once at [huggingface.co/black-forest-labs/FLUX.1-dev](https://huggingface.co/black-forest-labs/FLUX.1-dev) while signed in, *and* have that repo-read scope on the token. Miss either and you get the `MODEL_GATED` message.
2. `whoami-v2` answers for any valid token, so **the key will verify as "Connected" even if you forgot the Inference permission.** The failure then shows up on the first generation as `PROVIDER_AUTH`. If you see a green Connected badge but jobs fail on the key, that mismatch is the reason — not a stale token.

Hugging Face's settings wording shifts between UI revisions, so if a label reads slightly differently, go by the section names above.
