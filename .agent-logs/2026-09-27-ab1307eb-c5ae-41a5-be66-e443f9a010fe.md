## The one thing to read first

Probing the live database **with the public anon key**, four `SECURITY DEFINER` functions were executable by anonymous callers. Two of them moved money:

| Function | Impact |
| --- | --- |
| `admin_adjust_credits` | mint or claw back credits for any account, with a ledger row that made it look like an operator did it |
| `set_subscription_credits` | set any balance outright — **pre-existing**, from the billing work, not the CMS work |
| `admin_overview` / `admin_daily_series` | user counts, credits held, 30-day revenue |

Not theoretical: an anon-key call set one account's balance to 99999 and added a credit to another. Both reverted, along with the two ledger rows.

The cause is a Supabase trap. `revoke all on function f(...) from public` — which both migrations used, and which looks airtight — revokes the PUBLIC pseudo-role's grant, a grant these functions never had. Supabase's `alter default privileges` gives every new function in `public` an *explicit* grant to `anon` and `authenticated`. The revoke reported success and changed nothing.

Fixed in [0021_function_grants.sql](supabase/migrations/0021_function_grants.sql) (applied), guarded by [function-grants.sql](scripts/checks/function-grants.sql) — 22 checks, all passing:
