## What `<synthetic>` actually is

Claude Code writes `message.model: "<synthetic>"` on assistant records **it generates locally** rather than receiving from the API. In this session's transcript:

```

```

That single record, at line 1162:

Same story in the other two affected logs — `bf03dde9` and `2878e723` both have exactly one `<synthetic>` record, and both are session-limit notices.

## Why it poisons the whole exchange

In [capture.cjs:118](.claude/hooks/capture.cjs:118), the model is assigned on every assistant record carrying a text block, last-write-wins:

```js
if (rec.message && rec.message.model) current.model = rec.message.model
```

The limit notice *is* a text block, so it arrives last in exchange 1 and overwrites `claude-opus-5`. Then [line 161](.claude/hooks/capture.cjs:161) (`const m = p.model || model`) stamps that value on **both** the PROMPT and RESPONSE entries — which is why you see it on a prompt, where a model makes no sense at all.

There's a second symptom you may not have spotted: the notice is also pushed into `responseParts`, so line 376 of the log has "You've hit your session limit" sitting at the end of my answer as though I wrote it.

Exchanges 2 and 3 are correct because real records came after them. Note the frontmatter only reads `claude-opus-5` by luck — `lastModel()` takes the last pair with *any* model, so a session that ends on the limit notice would have `<synthetic>` at the top of the file too.

## The fix

One guard in `exchanges()` clears both symptoms:

```js
if (a !== null) {
  // Claude Code marks its own local notices — session limits, interrupts —
  // as `<synthetic>`. They are harness chrome, not an answer, so they
  // neither join the response body nor claim the model attribution.
  if (rec.message && rec.message.model === '<synthetic>') continue;
  current.responseParts.push(a)
  ...
}
```
